# StarNose
一个基于Node后端+VUE前端的个人数据嗅探工具，通过RSS订阅、爬虫、AI等技术，帮助用户节省自己每天检索大量平台数据的时间。现有版本是StarNose的第一个版本。

## 整体结构
StarNose由多个部分组成：
- UI模块，负责用户展示、设定与交互

- 网关模块，是UI模块的后台，通过webapi与UI模块交互。同时，开放标准数据接口以接收其他模块发送的数据并进行分析处理。

- 可独立运行和调用的数据源插件模块，是项目的plugins目录中的一个个独立文件夹。在网关模块启动时会扫描plugins目录，将存在的插件动态注册到网关模块中。在执行任务时，通过命令调度。


## 功能说明
### UI模块
- UI模块是指平台的纯前端部分，采用后台管理的展示风格，明亮的蓝白色配色；
- 不需要登录功能和界面；
- 左侧菜单依次为：数据源、规则、数据、分析、系统设置五个模块；

#### 数据源
- 采用APP ICON的形式横向动态排布注册成功的插件，每个插件下方都有一个setting按钮和一个history按钮，用户点击后可以进行调度频率设定；
- 当用户点击setting，弹出设定窗口，窗口中使用CRON设定一个调度频率，用户可选择窗口下方的ok和cancel按钮进行对应操作（设定的CRON是存储在数据库的）
- 当用户点击history时，弹出history历史调度记录，展示该插件的历史调度情况，包括最近10条调度记录，以及每条是否成功调度、总共获得多少数据、多少符合条件。

#### 规则
- 用来维护用户关心的数据描述，主体用列表页呈现，用户可新增规则；
- 列表页展示：规则名称、关键字、上次调度时间、操作栏（停用/启用，删除），列表页顶部有新增规则按钮；
- 当用户点击新增后，弹出新增窗口，有一个多行的富文本框，让用户详细描述他关心的数据是什么样子的，越详细越好（placeholder中要有体现）；新增窗口右下角显示下一步；
- 当用户填写完成并点击下一步时窗口冻结并显示待状态动画，系统从prompts文件夹中获取对应的提示词，并与用户的信息一同发给openrouter中对应的模型，由对应模型生成关键词；获得生成结果后，页面跳转到编辑设定窗口；
- 在编辑设定窗口中，用户可以看到生成的关键字，这些关键字会使用类似多标签的方式多行排布在一起，用户可以点击某一个关键字后的叉号将其删除；页面右下角是“重新设定”、“完成”、“取消”按钮；
- 当用户点击重新设定时，页面返回到新增窗口，保留原有用户填写内容，用户可以进行更改，更改后继续点击下一步，清空并重新生成关键字，其余操作逻辑与之前相同；
- 当用户点击完成时，系统显示等待，将该规则存储到数据库中；

#### 数据
- 数据模块展示符合条件并成功存储到数据库中的抓取数据，用列表的方式展示，提供多种查询条件，包括：按抓取时间范围查询、按数据发布时间查询、按插件（数据源）查询、按是已阅查询、按关键字查询（标题、正文都包括）；还包括多种排序，如按抓取时间正序&倒序，按发布时间正序、倒序。
- 默认查询条件仅有数据抓取时间，为用户当前时间之前的24小时范围内。
- 数据列表展示包括：序号、规则名称、数据源、标题、正文、关键字、抓取时间、发布时间、查阅状态；除展示字段外，还有一个跟踪按钮，该按钮表示后续继续跟踪该数据的变化。
- 用户可点击任意一行数据的任意位置进行查看详情，详情页面中罗列了所有字段的数据（后续数据规范中会有说明）；
- 所有列表必须分页，单页最大 100 条。

#### 分析
- 分析是一个大的分栏目分析功能，包括词频维度组成的词云，热点数据清单（自高而低），在顶部有抓取时间范围查询、数据源查询（多选）查询条件；
- 词云是在查询时间范围内，所有数据关键字的频率，主要以关键字的相近程度汇总展示，比如公鸡、母鸡都属于一类；
- 热点数据清单（自高而低）展示热度最高和最低的数据；

#### 设置
- 压力查看：暴露一个简单的“自检页面或接口”，显示插件注册数、调度队列长度、近期错误统计

### 网关模块
- 采用NodeJS实现，实现UI模块的后台接口、插件注册、集成接口与持久化、插件调度、数据分析等功能；
- 后台接口根据UI模块的要求实现；
- 插件注册：当项目启动时，网关模块扫描项目根目录下的plugins文件夹，并映射对应路径检查插件相关文件完整性，如果可以则注册到缓存中（纯服务器缓存，不使用redis，但缓存管理需要做一个独立包便于后期维护）；
- 集成接口：主要为各个插件提供后台端的配置读取功能，比如规则读取；也为各插件提供LLM（openrouter）能力的统一封装（包括提示词、模板等）；
- - 主要分为：数据存储接口、规则读取接口、数据获取接口、LLM数据验证接口几个部分;
- - 数据接收接口、规则读取接口根据后续数据库规范实现；
- - LLM数据验证接口，接收一个验证正文，然后由网关模块结合prompts文件夹中已经设定好的prompt向LLM请求验证，返回该数据是否符合用户要求的结果；
- - 数据跟踪接口，根据插件（数据源插件）返回用户在数据清单中点击跟踪的数据的唯一信息；
- 插件调度：网关模块内置一个调度器，根据用户对数据源的CRON配置，通过子线程调度插件，每次调度均为一次性调度，调度开始、进行、完成均作为插件对应的log文件持久化；插件执行的结果将通过网关的webapi回调传入；
- 数据分析，每一条获取到的数据都会得到关键字字段，以便于未来分析使用；
- 不做鉴权，默认所有插件都在可信环境本机运行；

### 独立运行的插件
- 独立运行的插件采用命令调用或映射调用的方式由网关模块调度运行；
- 每个独立插件均有自己独立的依赖，作为一个独立的项目；
- 每个插件均有标准的通用结构，如main文件main函数作为统一入口；每个插件均有自己的配置文件，包括名称、类型（当前仅有数据源插件）、版本、描述等信息；
- 每个独立的插件将根据需要实现特定数据源的集成功能，比如reddis插件等；
- 每个插件在运行时都会先根据自己的名称到网关模块中获取用户的规则配置，并使用规则配置匹配自己的数据，匹配过程：
- - 1，获取用户跟踪数据，通过网关的跟踪数据接口可获取用户点击跟踪数据的唯一值；
- - 2，过滤已存在的数据，每个通过的数据在发送给网关模块的数据接口时都会返回一个唯一值，该值将由插件自己存储在自己的跟踪列表中（物理文件存储），如果新的数据在该列表中并且不在用户跟踪数据列表中，则该值被抛弃；
- - 3， 关键字匹配，循环所有规则，根据规则模块中的关键字匹配数据，看是否存在，如果没有任何规则的关键字可以匹配成功，则数据丢弃；
- - 4， 内容匹配，当某一个规则的某一个关键字可以成功匹配时，则进入到内容匹配阶段，在内容匹配阶段，独立运行的插件将整个数据正文发送给网关模块，由网关模块请求LLM，确认数据是否符合要求并返回结果；另外，该数据不再进行其他规则匹配；
- - 5， 当内容匹配通过时，该数据将传送到网关模块的数据接收接口中，返回数据的唯一值（一般是标题或URLMD5实现）；热度值字段由插件自行逻辑定义；
- 插件运行过程均自行记录各步骤log，有完整的try cache避免崩溃，并记录log，不需要重试；
- 不做鉴权，默认所有插件都在可信环境本机运行；

### 网关与插件通信的设计
#### 网关职责
起一个 HTTP/REST 服务（NodeJS 很自然）。
对外（给插件）提供接口：
GET /api/rules?plugin=twitter：获取本插件需要的规则。
GET /api/tracking?plugin=twitter：获取用户跟踪列表。
POST /api/data：接收插件筛完、通过 LLM 验证的数据。
POST /api/validate：做 LLM 验证（插件发正文过来，网关转发给 LLM）。
未来还可以有：POST /api/log 用于插件上传自己的业务日志（可选）。
内部实现“LLM封装、持久化、分析”等。
#### 插件职责
自己是一个命令行程序（twitter-plugin.exe / python main.py / node main.js 都可以）。
启动时从环境变量或命令行参数里拿到：
网关地址（例如 GATEWAY_URL=http://localhost:3000）
当前调度 ID / 调度时间范围等。
整个运行流程大致是：
调 /api/rules 拿规则。
调 /api/tracking 拿跟踪列表。
自己去远程平台抓数据。
本地做去重（根据你说的“物理文件跟踪列表”）。
用规则关键字做粗筛。
命中规则的，把正文发给网关 /api/validate 做 LLM 验证。
通过的，发到 /api/data 存库。
在自己的 log 里记录整个过程（插件自管崩溃、try-catch）。
退出时用退出码标记成功/失败（0 成功，非 0 失败）。
####  调度方式
网关内置调度器（node 里用 node-cron 一类）。
到点后 spawn 插件进程，例如：
twitter-plugin --task-id=xxx --from=2024-02-26T00:00:00Z --to=2024-02-27T00:00:00Z
网关只负责：
记录“本次调度已启动/结束”的 log。
记录退出码/运行时长。
在 UI 的 history 界面展示“成功/失败/抓到多少数据”。
统一响应格式约定 

### 关于词云逻辑：
词云只用 keywords 字段做频次统计。
做简单的规范化（大小写、空白符）。
可以预留一个“人工近义词表”的扩展点，但不强求一开始就填很全。
分析查询只支持“时间范围 + 数据源多选”，不做过度组合条件。
```
简单归一化
全部转小写（针对英文）。
去掉标点、空格、特殊字符。
中英文可以做一些规则性的归并，例如：
全角/半角统一。
简体/繁体可以先不动，或者后面再加。
人工近义词表（可选）
手写一小份配置，例如：
{ "公鸡": "鸡", "母鸡": "鸡", "小鸡": "鸡" }
统计频次前，先把关键字用这张表做一个 map，统一到“标准词”上。
这张表可以放在网关的配置里，未来也可以提供 UI 维护。
```
